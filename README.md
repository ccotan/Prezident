## Чат по жалобе

Кнопка «Открыть обращение» теперь открывает отдельную страницу `#case/<id>`, а не модальное окно. Ссылку можно скопировать и повторно открыть; после входа в тот же аккаунт переписка остаётся доступной.

Автор жалобы и рассматривающие (Президент/Мин. Без.) могут отправлять сообщения и до четырёх HTTPS-ссылок на изображения. Решение со статусом записывается в историю переписки. Если жалоба удалена или аккаунту не разрешён доступ, показывается объяснение вместо пустого окна. Отправка неудачного сообщения не стирает введённый текст.

На настроенном сайте новые ответы проверяются каждые 10 секунд в активной вкладке; проверка не перезаписывает набираемый черновик. Это опрос сервера, не WebSocket и не push. Сеть/ошибки доступа отображаются строкой состояния; есть ручное обновление. Демо хранит только данные браузера: оно не является общим чатом между разными пользователями и компьютерами. Скопированная file://-ссылка не переносит записи другому человеку.

Чат использует complaints/complaint_messages из V3; фото — поля миграции V4. Новая схема доступа не расширяется: чужие обращения остаются закрыты RLS. На реальном Supabase после обновления нужно проверить обе роли отдельными аккаунтами.

## Новый запуск с нуля

### 1. Supabase

1. Создайте новый отдельный проект Supabase.
2. В SQL Editor выполните **`supabase/schema.sql` целиком один раз** на пустой базе. Это полная схема V4: дополнительно `upgrade-v2.sql`, `upgrade-v3.sql` и `upgrade-v4.sql` не нужны. Не применять поверх чужого приложения.
3. Authentication → Providers: включите Email и подтверждение почты. Настройте SMTP для реальных пользователей: встроенная тестовая отправка имеет ограничения.
4. Authentication → URL Configuration: Site URL = будущий адрес GitHub Pages с завершающим `/`, например `https://USERNAME.github.io/REPOSITORY/`. Добавьте тот же адрес в разрешённые Redirect URLs. Для локальной проверки добавьте `http://localhost:8000/`.
5. Оставьте стандартные email-шаблоны с `ConfirmationURL`. Сайт обрабатывает access_token/refresh_token в URL. Письма с произвольной схемой token_hash требуют адаптации.
6. Заполните `config.js` Project URL и публичным anon (legacy JWT) либо publishable key:

```js
window.PORTAL_CONFIG = {
  supabaseUrl: "https://YOUR-PROJECT.supabase.co",
  supabaseAnonKey: "YOUR-PUBLIC-ANON-OR-PUBLISHABLE-KEY"
};
```

**Никогда не помещайте service_role, secret key, пароль базы или GitHub token в сайт/репозиторий.** Публичный ключ безопасен только вместе с SQL-схемой и её правами доступа.

SQL создаёт публичный bucket `portal-media` с ограничением типов и размера. Читать изображения из bucket может каждый; загружать/удалять — только действующий Президент. Для отчётов сотрудники используют внешние HTTPS-ссылки. SVG запрещён. URL фотографий не является приватным секретом. Даже фото, прикреплённые к черновику, хранятся в публичном bucket и доступны по URL; приватность черновика относится к его тексту и записи в базе, а не к файлам Storage. Не загружайте конфиденциальные фото и документы с личными данными.

Блок кода поддерживается тройными обратными кавычками. Произвольный HTML/JavaScript не исполняется. Это ограниченный безопасный Markdown, не обещание поддержки всех комбинаций Discord.

3. Выберите цвет карточки и подпись. Добавьте до 4 фото: HTTPS-ссылками либо с устройства. Предпросмотр показывает результат; нижняя кнопка сохранения остаётся видимой.
4. Ctrl+Enter — публикация/сохранение. «Отмена» закрывает редактор **без сохранения**. Автосохранения новостей нет.
5. В «Законе» у Президента есть «Редактировать». «Сохранить черновик» — приватная запись в базе. «Опубликовать закон» — отдельное подтверждение и замена публичной редакции. Сохранение черновика не меняет опубликованный текст.
6. Изображения, загруженные до отмены редактора, могут остаться в Storage неиспользуемыми. Удалять их при необходимости можно через панель Supabase.

В демо фото с устройства ограничено **700 КБ** из-за localStorage; в общем сайте лимит 5 МБ. Для крупных фото в демо используйте HTTPS-ссылку. Хранение данных браузера также имеет общий лимит.

## Налоговая таблица

Скачивание XLSX/CSV убрано. Президент и Мин. Эко. могут импортировать ваш файл через «Налоги» → «Импорт XLSX».

Поддерживается первый лист `.xlsx` без пароля. Колонки:
- НИК / 👔 НИК;
- Номер / Номер 🎫;
- Дата обновления / 📅 Дата обновления;
- Оплачено **или** ⏱️ 7 дней;
- Доп. сведения (необязательно).

Статус и дата окончания рассчитываются сайтом заново. Формулы этих расчётных столбцов **игнорируются и не исполняются**. Формулы в исходных полях ника, номера, даты оплаты, признака оплаты или примечания блокируют импорт. Строки с пустыми ником/номером/датой пропускаются, даже если в них есть формулы шаблона или FALSE.

- До 5 МБ; 1–500 заполненных записей за импорт; до 2000 строк исходного листа.
- Ники: 2–16 латинских букв, цифр, `_`. Номер до 32 символов.
- Дата Excel (система 1900), `YYYY-MM-DD`, `DD.MM.YYYY`.
- Оплачено: Да/Нет, TRUE/FALSE, 1/0, Оплачено/Не оплачено. Пустое — нет.
- Совпавшие номера обновляются; новые добавляются. Начальный `№` при импорте убирается — используйте единый формат номеров. Дубли внутри одного файла блокируются.
- Сначала проверка и предпросмотр, затем подтверждение. Запись в настоящей базе одной транзакцией: ошибка не сохраняет половину файла.
- Деньги сайт не принимает. «+7 дн.» = отметить оплату сегодня на 7 календарных дней, а не прибавить к старому остатку. В 00:00 МСК даты окончания оплата уже истекла.

## Права

| Раздел/действие | Гость/обычный игрок | Министерства | Президент |
|---|---|---|---|
| Новости, министерства, налоги, опубликованный закон — чтение | Да | Да | Да |
| Отчёты — раздел и чтение | Нет | Да, только свой канал | Да |
| Публикация отчёта | Нет | Только свой канал | Любой канал |
| Удаление отчёта | Нет | Автор собственного отчёта | Любой |
| Публиковать/редактировать новости и закон | Нет | Нет | Да |
| Приватный черновик конституции | Нет | Нет | Да |
| Налоги — изменения и импорт | Нет | Мин. Эко. | Да |
| Жалоба — подать после входа | Да | Да | Да |
| Жалобы — читать | Только свои после входа | Свои, а Мин. Без. — все | Все |
| Ответ/статус жалобы | Нет | Мин. Без. | Да |
| Назначение ролей, глав, передача поста | Нет | Нет | Да |

Ограничения обеспечиваются таблицами, RLS и функцией `portal_action`. Прямые изменения таблиц браузерным ключом запрещены. Президент определяется по UUID, не по localStorage/нику. Простая правка интерфейса не выдаёт прав в реальной базе. Доступ к отдельным министерским каналам изолирован и на чтение, и на запись. Президент видит все каналы.

Публичный налоговый реестр по-прежнему можно прочитать через браузер/API — удаление кнопок выгрузки не является запретом копирования публичных данных. JSON-снимок в панели Президента — административный снимок доступных реестров, не XLSX/CSV и не полная резервная копия аккаунтов. Храните его приватно, там есть жалобы.

## Приёмка после развёртывания

Проверить на настоящем проекте и разных аккаунтах:
1. Гость и обычный игрок не видят «Отчёты», `#reports` не открывается, API reports не возвращает строки.
2. Министр читает и пишет только в свой канал; прямой RPC чужого канала отклоняется.
3. Обычный игрок не может менять новости/закон/роли/налоги ни через интерфейс, ни запросом.
4. Черновик закона не виден гостю/министру через REST, опубликованный закон виден. Сохранение нового черновика не меняет опубликованную редакцию.
5. Загрузка в `portal-media` разрешена Президенту, отклоняется для других; запрещены SVG и файл больше 5 МБ.
6. Другой браузер после «Обновить» видит отредактированную новость, опубликованный закон и налоги.
7. Подтверждение почты, восстановление/смена пароля и передача поста работают с вашим доменом.
8. Старые роли/жалобы/новости сохранились после `upgrade-v2.sql`.

В текущей среде проверены локальные сценарии, сам приложенный XLSX, мобильная версия и запросы серверного режима на **имитации API**. Реальный Supabase/PostgreSQL, SMTP, GitHub Actions и доступность реальных Minecraft-скинов здесь не проверялись. Не считайте тест интерфейса аудитом серверной безопасности.

## Ограничения

Нет автоматической выдачи ролей на игровом сервере, связи с Discord, приёма платежей, истории редакций/аудита действий. Общие данные обновляются при открытии, по кнопке и после своей записи; WebSocket-обновлений нет. Чужие изменения видны после обновления, которое может сбросить несохранённый черновик отчёта/настроек. При одновременном изменении записи последняя успешная запись побеждает. Авторы исторических публикаций сохраняются.

Для небольшого сообщества. Есть ограничение 10 жалоб в час на аккаунт, но не защита от массовых регистраций. Перед массовым запуском настройте CAPTCHA/SMTP/rate limits, резервные копии и пройдите аудит. Сессия хранится в localStorage — не используйте чужой компьютер и непроверенные скрипты на этом домене. Ники не подтверждают Minecraft-владение. Публичные изображения и внешние доказательства могут иметь собственные правила доступа.

## Приёмка V3 на реальном Supabase

Проводите с отдельными аккаунтами, а не только переключением демо.

- Гость/игрок: `GET /rest/v1/reports?select=*`, ministry_tasks, law_drafts и action_log возвращают пустые массивы. Чужие complaints/complaint_messages/notifications тоже не видны.
- Мин. Эко.: reports и ministry_tasks возвращают только channel=eco; даже запрос `channel=eq.inf` пуст. RPC report_add/report_update/report_delete против inf/bez отклоняется. Даже старый собственный отчёт из другого министерства после перевода не доступен.
- Президент: видит все каналы/задачи и журнал; может публиковать закон и указы.
- Глава Мин. Эко.: team_add со свободным игроком принимает его в eco даже при подмене channel; team_remove чужого сотрудника/главы и role_set отклоняются. Рядовой сотрудник не может выполнять team_add/remove.
- Игрок: complaint_message только в своей жалобе; жалоба другого игрока недоступна. Решение/отклонение без причины отклоняется.
- task_update чужой задачи, статус done/cancelled от министерства и прикрепление отчёта другого канала отклоняются. Закрытая задача не изменяется сотрудником.
- Дубликат номера указа (без учёта регистра) отклоняется; отмена без причины отклоняется.
- Прямые INSERT/UPDATE/DELETE во все таблицы от anon/authenticated запрещены. Изменения только через portal_action; нельзя напрямую вставить поддельное уведомление или событие журнала.
- После передачи поста новый Президент получает полномочия, старый их теряет; новый Президент исключён из состава министерства.
- Уведомления доступны только получателю. После перевода чужие канальные уведомления больше не возвращаются.
- Проверьте реальную почту/восстановление пароля, Storage, буфер обмена под HTTPS и загрузку голов mc-heads.net. Локальное тестирование их доступность не подтверждает.

## V4.3 — регистрация, Discord и поиск состава

### Что изменилось
- Раздел «Указы» убран из меню и страниц. Старые документы не удаляются из базы: они остаются в новостях. Ссылки `#decrees` и старые уведомления перенаправляются в новости.
- В окне входа есть переход к отдельной странице `#register`: Minecraft-ник, почта, пароль и подтверждение пароля. Обычный новый пользователь не получает прав Президента или министерства.
- Для общего сайта используется **Supabase Auth**, включая подтверждение почты и существующее восстановление пароля. Пароли не пишутся в реестры, журнал, снимок JSON или localStorage. В localStorage серверного режима остаётся сессия Supabase, как и прежде.
- В автономном HTML регистрация создаёт только локальный демо-профиль без сохранения почты и пароля. Это не настоящая авторизация и не защита ролей. Не вводите туда настоящие пароли.
- В личном кабинете добавлен Discord как **самостоятельно введённый контакт, без OAuth и подтверждения владельца**. Контакт хранится отдельно от публичного списка игроков. В серверном режиме RLS разрешает читать его только владельцу; RPC изменяет только запись `auth.uid()`. Удалить контакт можно в той же карточке. Имя Discord не даёт возможности входа на сайт.
- При наборе в министерство вводите ник в поиске. Поиск без учёта регистра показывает максимум 8 совпадений; при точном нике игрок сразу выбран. В результатах только свободные зарегистрированные игроки, не Президент и не главы/сотрудники. Права главы ограничены своим министерством, как и прежде.

### Установка V4.3
1. Если сайт уже использует V4/V4.1/V4.2: выполните **supabase/upgrade-v4.3.sql** в SQL Editor своего Supabase, затем замените файлы сайта. Миграция создаёт приватную таблицу контактов и RPC; старые профили и публикации не удаляет.
2. Для нового проекта выполните **supabase/schema.sql**: в нём уже есть схема контактов. Для более ранней V3 сначала примените upgrade-v4.sql согласно предыдущей инструкции.
3. Заполните config.js URL своего проекта и публичным anon/publishable ключом. Secret/service_role ключи в сайт не добавлять.
4. В Supabase Authentication включите регистрацию Email/Password, при необходимости Confirm email. Настройте SMTP/лимиты доставки и проверьте настоящее письмо.
5. В Authentication → URL Configuration задайте Site URL опубликованного HTTPS-сайта и добавьте точный адрес страницы портала (включая путь репозитория) в Redirect URLs. Форма передаёт этот адрес как redirect_to. При неправильном allowlist используется поведение Supabase; проверяйте возврат по письму после публикации.
6. Проверьте регистрацию, подтверждение, вход, восстановление пароля и сохранение/удаление Discord в двух настоящих аккаунтах. Реальные почтовая доставка, SQL/RLS и Discord OAuth в локальных тестах не выполнялись; OAuth не реализован.

## V4.4 — настоящая привязка Discord (заменяет ручной контакт V4.3)

Теперь в кабинете используется штатная OAuth identity Discord в Supabase Auth, а не введённый вручную ник. Привязка/отвязка сохраняют прежний user ID, Minecraft-профиль и права. Проверенный статус читается с Auth-сервера, не из редактируемых метаданных. В автономном демо настоящий OAuth не выполняется.

**Полная инструкция: DISCORD_SETUP.md.** Создайте приложение Discord, задайте callback Supabase, включите Discord provider и Manual Linking, добавьте точный redirect портала с `?discord_link=1`, затем установите discordOAuthEnabled=true в config.js. Client Secret — только в Supabase Dashboard; отдельный бот, Edge Function и service_role ключ для этой привязки не нужны. Примените upgrade-v4.4.sql для отключения старого ручного RPC; старые контакты остаются приватными, но не используются и не считаются подтверждёнными.

В этой версии нет отдельной кнопки регистрации/первичного входа через Discord: сначала email-аккаунт с Minecraft-ником, затем привязка в кабинете. Нативная identity, как и другие способы Supabase Auth, может служить способом входа; управление такой возможностью зависит от настроек проекта. Поведение живого provider обязательно проверить после настройки.
